# 设备诊断

## 做了什么

虾小丘通过飞书帮用户诊断开博尔数播设备的缺陷：
- 用户发 MAC 地址后 4 位 → 虾小丘自动拉取服务器日志
- 用户选一个 zip → 虾小丘下载并按 8 步标准流程分析
- 最终输出诊断报告，归档到飞书云盘

## 核心思路

### 诊断流程

```
用户发 MAC (如 D0:87:80)
  → SSH 连日志服务器
  → ls -1t 列出该设备的所有日志 zip（按时间倒序）
  → 只返回文件名列表，不做额外分析
  → 等用户说「分析 xxx.zip」
  → 下载 → 解压 → 8步分析 → 输出报告
  → 删除解压目录
  → 可选：保存到飞书云盘
```

### 多维度交叉验证

诊断不止看报错日志，需要多维度交叉验证：

| 维度 | 信息来源 | 判断标准 |
|------|---------|---------|
| 播放状态 | realStart/onCompletion/onError | 播放链是否完整 |
| UI状态 | NavBar session state (1/2/3) | 界面是否在播放状态 |
| 网络流量 | netstats_wifi 首尾差值 | 是否真的在拉流/下载 |
| 音频焦点 | requestAudioFocus/abandonAudioFocus | 有无被其他 app 抢占 |
| 系统资源 | perf_snapshot top/meminfo | 是否卡顿/内存不足 |

### 已分析的问题类型

5 个典型缺陷的根因各不相同：
- **封面解码故障** → UI 卡顿（BitmapFactory 解码失败）
- **WebRTC 崩溃** → libjingle SIGSEGV（投屏服务 C++ 层）
- **继电器咔咔响** → USB Audio HAL standby（硬件驱动层）
- **音量条拖拽中断** → 播放器重启 + USB 重协商（跨进程状态同步）
- **UI 残留** → metadata 异步更新竞态（时序问题）

## 复用指南

### 新设备诊断流程迁移

**只需要换**：
1. SSH 服务器地址和日志路径
2. grep 关键词（设备特定的包名、错误标识、播放状态标识）
3. 维度表（换新设备的关键指标）

**不需要换的**：
- MAC→列表→选择→分析的四步交互流程
- 多维度交叉验证的思路
- 分析陷阱（KeepAlive ≠ 在播放、日志裁剪误判）

### 多维度验证模板

```markdown
## 验证维度

| 维度 | 数据来源 | 判断标准 |
|------|---------|---------|
| [维度1] | [日志来源] | [正常/异常标准] |
| [维度2] | [日志来源] | [正常/异常标准] |
| [维度3] | [日志来源] | [正常/异常标准] |

## 分析陷阱
- [陷阱1]：[原因和规避方式]
- [陷阱2]：[原因和规避方式]
```

**新项目直接填表**，维度越多交叉验证越准确。
