## 做了什么

虾小丘通过飞书帮用户诊断开博尔数播设备的缺陷：

```
用户发 MAC (如 D0:87:80)
  → SSH 连服务器 → ls -1t 列出日志 zip
  → 只返回文件名，不做额外分析
  → 等用户说「分析 xxx.zip」
  → 下载 → 解压 → 8步分析 → 输出报告 → 删解压目录
  → 可选：保存到飞书云盘
```

## 核心思路

### 多维度交叉验证

> 💡 诊断不止看报错日志，需要**多维度交叉验证**。

| 维度 | 信息来源 | 判断标准 |
|------|---------|---------|
| **播放状态** | `realStart` / `onCompletion` / `onError` | 播放链是否完整 |
| **UI 状态** | NavBar session state (1/2/3) | 界面是否在播放状态 |
| **网络流量** | `netstats_wifi` 首尾差值 | 是否真的在拉流/下载 |
| **音频焦点** | `requestAudioFocus` / `abandonAudioFocus` | 有无被其他 app 抢占 |
| **系统资源** | `perf_snapshot` top/meminfo | 是否卡顿/内存不足 |

───

### 已分析的问题类型

| # | 问题 | 根因类型 |
|---|------|---------|
| 1 | 封面解码故障 → UI 卡顿 | BitmapFactory 解码失败（应用层） |
| 2 | WebRTC SIGSEGV 崩溃 | libjingle 投屏服务异常（C++ 层） |
| 3 | 继电器咔咔响 + 播放断断续续 | USB Audio HAL standby（硬件驱动层） |
| 4 | 音量条拖拽中断播放 | 播放器重启 + USB 重协商（跨进程同步） |
| 5 | 播放 session 切换 UI 残留 | metadata 异步更新竞态（时序问题） |

## 🔄 复用指南

### 新设备诊断只需换三个东西

| 需要改 | 不需要动 |
|---------|---------|
| SSH 服务器地址和日志路径 | MAC→列表→选择→分析 的四步交互流程 |
| grep 关键词（设备包名、错误标识、播放状态标识） | 多维度交叉验证的思路 |
| 维度表（换新设备的关键指标） | 分析陷阱提醒 |

### 多维度验证模板

```markdown
## 验证维度

| 维度 | 数据来源 | 判断标准 |
|------|---------|---------|
| [维度1] | [日志来源] | [正常/异常标准] |
| [维度2] | [日志来源] | [正常/异常标准] |

## 分析陷阱
- [陷阱1]：[原因和规避方式]
- [陷阱2]：[原因和规避方式]
```

**新项目直接填表**，维度越多交叉验证越准确。
