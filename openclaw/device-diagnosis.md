## 做了什么

虾小丘通过飞书帮用户诊断开博尔数播设备缺陷：

> **诊断流程**
>
> 1. 用户发 MAC 后 4 位（如 D0:87:80）
> 2. SSH 连服务器 → `ls -1t` 按时间倒序列出该设备所有日志 zip
> 3. **只返回文件名**，不做额外分析
> 4. 等用户说「分析 xxx.zip」
> 5. 下载 → 解压 → 8 步分析 → 输出报告
> 6. 删除解压目录（只保留 zip）
> 7. 可选：保存到飞书云盘

> [!IMPORTANT]
> 诊断不止看报错日志，需要**多维度交叉验证**：播放状态 + UI 状态 + 网络流量 + 音频焦点 + 系统资源。不全信单一指标。

───

### 多维度验证

- **播放状态**：`realStart`/`onCompletion`/`onError` — 播放链是否完整
- **UI 状态**：NavBar session state (1/2/3) — 界面是否在播放状态
- **网络流量**：`netstats_wifi` 首尾差值 — 是否真的在拉流
- **音频焦点**：`requestAudioFocus`/`abandonAudioFocus` — 有无被抢占
- **系统资源**：`perf_snapshot` top/meminfo — 是否卡顿

───

### 已分析的典型问题

| # | 问题 | 根因层 |
|---|------|--------|
| 1 | 封面解码故障 → UI 卡顿 | 应用层（BitmapFactory） |
| 2 | WebRTC SIGSEGV 崩溃 | C++ 层（libjingle） |
| 3 | 继电器咔咔响 + 播放断断续续 | 驱动层（USB Audio HAL） |
| 4 | 音量条拖拽中断播放 | 跨进程同步问题 |
| 5 | session 切换 UI 残留 | 时序竞态条件 |

## 复用指南

> [!TIP]
> **新设备只需换 3 个东西**：SSH 地址/路径、grep 关键词、维度表指标。四步交互流程和交叉验证思路完全复用。

```markdown
## 验证维度
- [维度1]：[数据来源] — [正常/异常标准]
- [维度2]：[数据来源] — [正常/异常标准]

## 分析陷阱
- [陷阱]：[原因和规避方式]
```

新项目直接填维度表，维度越多交叉验证越准。
